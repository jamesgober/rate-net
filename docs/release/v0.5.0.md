# rate-net v0.5.0 — Feature complete

**Everything a consumer needs, and features frozen.** v0.5.0 rounds out the crate: runnable examples for every use case, an optional async *await-until-ready* layer, and a baseline Criterion suite with recorded numbers. With the algorithm suite (0.4) over the sharded, bounded-memory, allocation-free core (0.3), the surface is now complete — the remaining road to `1.0` is optimization, hardening, and the stability soak, not new features.

## What is rate-net?

A powerful, lock-free rate limiter for Rust. It answers one question as fast as the hardware allows — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. Five algorithms behind one `Limiter` trait, per-key state in a sharded store bounded by eviction, time from an injectable [`clock-lib`](https://crates.io/crates/clock-lib) clock, and token-bucket accounting delegated to [`better-bucket`](https://crates.io/crates/better-bucket). It is the anchor crate of the `-net` domain group.

## What's new in 0.5.0

### `AsyncLimiter` — await until allowed

The core is sync and runtime-free: `check` never blocks, so most async callers just call it and shed load on a denial. Behind the optional `async` feature, `AsyncLimiter` adds the one thing that genuinely needs a runtime — *waiting* for a key to become allowed:

```rust
use rate_net::{AsyncLimiter, RateLimiter};

# async fn demo() {
let limiter = AsyncLimiter::new(RateLimiter::per_second(100));

// Non-blocking, same as the sync API.
let _ = limiter.check("user:42");

// Or await until the key is within its limit.
limiter.until_ready("user:42").await;
# }
```

`until_ready` retries on each denial, sleeping for the reported `retry_after` via `tokio::time`, until the key is admitted — and gives up immediately, rather than waiting forever, when a request can never succeed. Only this layer touches a runtime; the core never depends on one.

### Runnable examples

Self-contained demos in [`examples/`](https://github.com/jamesgober/rate-net/tree/main/examples), covering the use cases from the roadmap:

```text
cargo run --example per_second    # Tier-1: N requests/second per key
cargo run --example per_key       # per-IP and per-user, independent allowances
cargo run --example mock_clock    # deterministic refill with a ManualClock, no sleeping
cargo run --example retry_after   # mapping a denial to HTTP 429 + Retry-After

cargo run --example algorithms --features algorithms  # compare all five algorithms
cargo run --example async_wait   --features async      # await until allowed
```

### Baseline benchmark suite

The Criterion suite ([`benches/rate_bench.rs`](https://github.com/jamesgober/rate-net/blob/main/benches/rate_bench.rs)) covers the four paths that matter — `single_key`, `many_keys` (shard scaling), `contended_single_key` (4 threads), and `eviction_sweep` — with baseline numbers recorded in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md):

| Path | Median |
|------|-------:|
| Single-key check | ~77 ns |
| Many-key check (64 shards) | ~99 ns |
| Contended single key (4 threads) | ~76 ns/op |
| Eviction sweep (cold insert at cap) | ~287 ns |

These are the **pre-optimization** baseline: `0.6` fuses the two key hashes into one keyed hash, swaps in a faster hasher, and adds the head-to-head comparison against `governor`.

### Feature freeze

The public surface is complete and frozen. Subsequent pre-1.0 releases are optimization, hardening, and stabilization only — no new features.

## Breaking changes

None. `AsyncLimiter` and the examples are additive; the async wrapper is gated behind the (already-declared) `async` feature, whose `tokio` dependency was trimmed to just its timer.

