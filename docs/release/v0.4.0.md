# rate-net v0.4.0 — Extended

**The full algorithm suite, behind one trait.** v0.4.0 adds four algorithms beyond the default token bucket — a leaky bucket (GCRA), a fixed window, a sliding-window log, and a sliding-window counter — each a `Limiter` implementation with its own `proptest` over-admit proof and retry-after tests. A new Tier-2 builder selects the algorithm, quota, burst, shard count, eviction policy, and clock in one fluent surface. The extra algorithms live behind the opt-in `algorithms` feature, so the default build stays lean (token bucket only) and is now exercised in CI alongside `--all-features`.

## What is rate-net?

A powerful, lock-free rate limiter for Rust. It answers one question as fast as the hardware allows — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. Per-key state lives in a sharded, bounded-memory store with an allocation-free steady-state check; the token bucket delegates to [`better-bucket`](https://crates.io/crates/better-bucket) and time comes from [`clock-lib`](https://crates.io/crates/clock-lib). It is the anchor crate of the `-net` domain group.

## What's new in 0.4.0

### Four more algorithms, one `Limiter` trait

Each is selected at runtime through the [`Algorithm`](https://docs.rs/rate-net/latest/rate_net/enum.Algorithm.html) enum, dispatched by a plain `match` (no boxing, no vtable), so adding them costs nothing on the token-bucket path.

- **Leaky bucket (GCRA).** Where the token bucket lets a full burst through and then sustains, the leaky bucket *spaces* admitted units at least one emission interval apart, smoothing toward a steady output rate while still tolerating the quota's `burst`. Lock-free: one atomic theoretical-arrival-time advanced by compare-and-swap.
- **Fixed window.** The cheapest option — a lock-free packed `(window, count)` atomic that resets at each boundary. Tolerates the classic fixed-window burst (up to `2 × limit` across a boundary).
- **Sliding-window log.** Exact: it keeps the timestamp of every admitted unit in the trailing window and never bursts at a boundary. Memory is bounded by `limit` per key.
- **Sliding-window counter.** O(1) and approximate — a time-weighted blend of the current and previous window's counts. The common production middle ground; the true rolling count stays within `2 × limit`.

```rust
use rate_net::{RateLimiter, Algorithm};

let limiter = RateLimiter::per_second(100).with_algorithm(Algorithm::SlidingWindowLog);
assert!(limiter.check("user:42").is_allow());
```

### Tier-2 builder

`RateLimiter::builder()` folds every knob into one place:

```rust
use rate_net::{RateLimiter, Algorithm, Eviction};
use std::time::Duration;

let limiter = RateLimiter::builder()
    .algorithm(Algorithm::SlidingWindowCounter)
    .quota(1000, Duration::from_secs(60)) // 1000 / minute
    .burst(50)                            // allow short bursts of 50
    .shards(64)                           // tune for core count
    .eviction(Eviction::idle(Duration::from_secs(300)))
    .build();
```

`build()` is infallible. The same knobs remain available as chainable adjusters (`with_algorithm`, `with_shards`, `with_eviction`, `with_clock`) for callers who prefer them.

### `burst` on `Quota`

`Quota` now carries a `burst` ceiling distinct from the sustained `limit` — the most a key may spend at once. It defaults to `limit` (the classic "burst equals rate" bucket) and is honoured by the token and leaky buckets; the window algorithms admit at most `limit` per `period` and ignore it.

```rust
use rate_net::Quota;
use std::time::Duration;

// Sustain 1000/min but never let a key spend more than 50 at once.
let quota = Quota::rate(1000, Duration::from_secs(60))?.with_burst(50);
# Ok::<(), rate_net::RateLimiterError>(())
```

### Proven, per algorithm

`tests/proptest_algorithms.rs` exercises each algorithm through the full `RateLimiter` on a deterministic clock, asserting its specific over-admit bound across arbitrary interleavings of checks and time advances: fixed window and sliding-log never exceed `limit` (exact), and the sliding counter and leaky bucket stay within their `2 × limit` worst case. Every algorithm also has deterministic unit tests for window rollover and retry-after accuracy.

## Breaking changes

The token-bucket surface is unchanged. The additions — the four `Algorithm` variants, the `Builder`, `RateLimiter::with_algorithm`, and `Quota::burst` / `with_burst` — are additive, and the new algorithm variants are gated behind the opt-in `algorithms` feature. Pre-1.0, surface changes still bump the MINOR version and are noted here.
