# rate-net v0.9.5 — Release Candidate

**The beta is clean.** The soak surfaced no bugs and no friction from real consumption. v0.9.5 is the release candidate: critical fixes and documentation polish only before `1.0`. Pin `rate-net = "0.9"` for the RC and upgrade to `1.0` without source changes.

## What is rate-net?

A powerful, lock-free rate limiter for Rust. It answers one question as fast as the hardware allows — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. Five algorithms behind one `Limiter` trait, per-key state in a sharded store bounded by eviction, hardened against adversarial traffic, with a frozen public API validated against a representative gatekeeper consumer.

## What's new in 0.9.5

### Final benchmarks — no regression

Criterion means re-captured at the RC tag on Windows x86_64 (Rust stable, `opt-level = 3`):

| Path | v0.6.0 (recorded) | v0.9.5 |
|------|------------------:|-------:|
| Single-key check | ~54 ns | ~55 ns |
| Many-key check (64 shards) | ~54 ns | ~56 ns |
| Contended single key (4 threads) | ~54 ns/op | ~57 ns/op |
| Eviction sweep | ~217 ns | ~215 ns |

All four tracked paths are within roughly ±2 ns of the `0.6.0` baseline — sample-to-sample variance, not a regression. The honest head-to-head against `governor` is unchanged: rate-net's per-key overhead is competitive once the clock is held equal, and beating `governor` end-to-end still needs a fast TSC-style monotonic source in `clock-lib` (raised separately). The full analysis is in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md).
