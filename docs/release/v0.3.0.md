# rate-net v0.3.0 — Core

**The real concurrent machine.** v0.3.0 replaces the placeholder map behind the limiter with a purpose-built **sharded per-key store**: unrelated keys live in different shards and never contend, an existing-key check takes only a shard read lock plus the bucket's own atomic accounting, and the steady-state check path is **allocation-free**. Memory is **bounded by eviction** — a lazy, per-shard LRU-plus-idle-TTL sweep that runs while inserting a new key, so a flood of unique keys hits a cap instead of growing without limit, with no background thread and no whole-store pause. The hard guarantees are backed by proof: a `loom` model of the store protocol, a multi-threaded stress test, and an allocation audit.

## What is rate-net?

A powerful, lock-free rate limiter for Rust. It answers one question as fast as the hardware allows — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key under high contention. It does not re-implement token-bucket math: it consumes [`better-bucket`](https://crates.io/crates/better-bucket) for that and reads time from [`clock-lib`](https://crates.io/crates/clock-lib), then adds the per-key, multi-algorithm, bounded-memory machinery around them. It is the anchor crate of the `-net` domain group.

## What's new in 0.3.0

### Sharded per-key store

Per-key state now lives in a sharded store built for this job. A key is hashed to one of a power-of-two number of shards, each guarded by its own `RwLock`. The win is on the hot path: an existing-key check takes a shard **read** lock and lets the key's bucket do its own compare-and-swap, so unrelated keys — and concurrent checks of the *same* key — proceed without serialising. Only first-seeing a key takes the brief write lock. The shard count is configurable and defaults to a small multiple of the core count:

```rust
use rate_net::RateLimiter;

let limiter = RateLimiter::per_second(1000).with_shards(64);
assert_eq!(limiter.shards(), 64);
```

### Bounded-memory eviction

A rate limiter that tracks state per key is a denial-of-service vector against itself if that state can grow without limit. The new `Eviction` policy is the defense. Two bounds compose — a hard **capacity** cap (the least-recently-seen key is evicted to make room) and an **idle TTL** (keys not seen for longer than the TTL are reclaimed) — and the default is safe out of the box: a `DEFAULT_MAX_KEYS` cap, no TTL.

Eviction is **lazy and per-shard**. It happens while inserting a new key, under the write lock already held, and only ever looks at the one shard being written — never the whole store, never a background timer, never a stop-the-world pass on the hot path.

```rust
use rate_net::{RateLimiter, Eviction};
use std::time::Duration;

let limiter = RateLimiter::per_second(1000)
    .with_eviction(Eviction::capacity(100_000).with_idle(Duration::from_secs(300)));
assert_eq!(limiter.eviction().max_keys(), Some(100_000));
```

### Allocation-free steady state

`Key` now stores its bytes inline for the common identities — IP addresses, `u64` ids, short string keys — spilling to the heap only for unusually long keys. Combined with the read-lock fast path, a check on a key that already has state performs **zero heap allocations**, asserted by a per-thread allocation audit over a 200k-iteration steady-state loop.

### Proven under concurrency and load

- **`loom`** exhaustively explores the store's get-or-insert protocol: two threads racing to first-touch the same key share a single bucket (never a duplicate) and never over-admit.
- **Stress test** — with the clock frozen so no refill occurs, eight threads hammer 64 keys far past their quota; every key is admitted *exactly* its quota: never more (no over-admit) and never fewer (no lost decrement).
- **Eviction tests** — a 50k unique-key flood stays within the configured cap; idle keys are reclaimed on a later insert into their shard; and a continuously-touched "hot" key is never the eviction victim under capacity pressure.

### Introspection

`RateLimiter::shards()` and `RateLimiter::eviction()` join `quota()`, `algorithm()`, and `tracked_keys()`. The `Debug` impl reports the configuration and the live key count — never the keys themselves, which can be caller identities.

## Breaking changes

The public type surface is unchanged from `0.2.0`; `Eviction`, `DEFAULT_MAX_KEYS`, and the `with_shards` / `with_eviction` / `shards` / `eviction` methods are additive. Internally, the `dashmap` dependency was **replaced** by the purpose-built store — which is what makes per-shard incremental eviction and the read-lock steady-state path possible — so `dashmap` is no longer in the dependency tree. Pre-1.0, surface changes still bump the MINOR version and are noted here.
