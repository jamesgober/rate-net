# rate-net v0.2.0 — Foundation

**The public shape is locked, and the one-line limiter works.** v0.2.0 turns the scaffold into a usable crate: `RateLimiter::per_second(n)` then `limiter.check(key)` answers an allow/deny-plus-`retry-after` decision today, backed by a token bucket and an injectable clock. It introduces the types every later phase is built on — the `Decision` result, the `Quota` and `Algorithm` configuration types, the `RateLimiterError`, the `Key` identity, and the `Limiter` trait — and proves the core safety invariant with `proptest`. Per-key state currently lives in a concurrent map; the tunable sharded store with bounded-memory eviction and the zero-allocation steady state arrive in `0.3.0`. Zero breaking changes that matter — the only prior release was the scaffold.

## What is rate-net?

A powerful, lock-free rate limiter for Rust. It answers one question as fast as the hardware allows — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. It does not re-implement token-bucket math: it consumes [`better-bucket`](https://crates.io/crates/better-bucket) for that and reads time from [`clock-lib`](https://crates.io/crates/clock-lib), then adds the per-key, multi-algorithm, retry-after machinery around them. It is the anchor crate of the `-net` domain group.

## What's new in 0.2.0

### `RateLimiter` — the keyed limiter

The headline type. One call to construct, one to check:

```rust
use rate_net::{RateLimiter, Decision};

let limiter = RateLimiter::per_second(100);

match limiter.check("user:42") {
    Decision::Allow => { /* serve the request */ }
    Decision::Deny { retry_after } => { /* 429 with Retry-After */ let _ = retry_after; }
    _ => {}
}
```

`per_second` and `per_minute` are the infallible Tier-1 constructors; `with_quota` takes an explicit [`Quota`]. The request path is `check(key)` / `check_n(key, n)` — the key is anything that converts into a `Key` (a `&str`, `String`, byte slice, `u64`, or `IpAddr`), and `check_n` takes several units at once for batches or weighted endpoints. The limiter is `Send + Sync`, takes `&self` on the check path, and is meant to be shared across request-serving threads. Its `Debug` impl prints the quota, algorithm, and live key count — never the keys, which can be caller identities.

### `Limiter` trait

The shared surface every algorithm implements, so generic code can hold any limiter without naming its concrete type or clock:

```rust
use rate_net::{Limiter, RateLimiter};

fn admit_one<L: Limiter>(limiter: &L, key: &str) -> bool {
    limiter.check(key).is_allow()
}

assert!(admit_one(&RateLimiter::per_second(2), "user:1"));
```

### `Decision`, `Quota`, `Algorithm`, `RateLimiterError`, `Key`

The locked configuration and result types, each `#[non_exhaustive]` where it will grow:

- **`Decision`** — `Allow` / `Deny { retry_after }`, with `is_allow` / `is_deny` / `retry_after` helpers and a `From<better_bucket::Decision>` bridge.
- **`Quota`** — `per_second` / `per_minute` (infallible) and the validated `rate(limit, period)` constructor.
- **`Algorithm`** — the selector; defaults to `TokenBucket`, the only variant wired in this release. Leaky bucket, fixed window, and the sliding-window algorithms are named for `0.4`.
- **`RateLimiterError`** — `ZeroQuota` / `ZeroPeriod`, implemented on `error-forge`'s `ForgeError` so it carries the same `kind` / `caption` / `is_retryable` metadata as every other domain error in the portfolio.
- **`Key`** — the opaque per-key identity, equal by byte content, with `From` conversions for the common identity types.

### Deterministic time

The clock is injectable. In production it is the OS monotonic clock; in tests a `ManualClock` advances on demand, so window and refill behaviour is exercised without ever sleeping:

```rust
use rate_net::RateLimiter;
use clock_lib::ManualClock;
use std::sync::Arc;
use std::time::Duration;

let clock = Arc::new(ManualClock::new());
let limiter = RateLimiter::per_second(5).with_clock(Arc::clone(&clock));

for _ in 0..5 {
    assert!(limiter.check("k").is_allow());
}
assert!(limiter.check("k").is_deny());

clock.advance(Duration::from_secs(1)); // no real sleep
assert!(limiter.check("k").is_allow());
```

### The over-admit invariant, in `proptest`

The defining correctness property — **a key is never admitted beyond its quota** — is now a property test. Across any interleaving of checks and whole-second time advances, the number admitted for a key never exceeds the initial burst plus one refill per elapsed second; and across many distinct keys, draining one never spends another's allowance. The concurrent-interleaving variant of this proof is model-checked with `loom` (the CAS admit kernel today; the full per-key sharded model lands in `0.3.0`).

## Breaking changes

**None of consequence.** The only prior release was the `0.1.0` scaffold, which exposed only `VERSION`. Pre-1.0, the public surface may still change as the roadmap progresses; such changes will bump the MINOR version and be called out here.

## Verification

Run on Windows x86_64 (Rust stable 1.95.x and the 1.85 MSRV toolchain); the same commands pass on Linux (WSL2 Ubuntu) and across the configured CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo build --no-default-features            # no_std build (exposes only VERSION)
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
RUSTFLAGS="--cfg loom" cargo test --test loom_check
cargo audit
cargo deny check
```

All green. Counts at this tag:

- Default features and `--all-features`: 33 unit tests + 27 rustdoc tests + 2 property tests.
- Under `--cfg loom`: 1 concurrency model test.

## What's next

- **0.3.0 — Core.** The real concurrent machine: a tunable sharded per-key store with a zero-allocation steady state, incremental LRU/TTL eviction so a unique-key flood hits a memory cap instead of growing unbounded, and the `loom` + eviction-under-load proofs.
- **0.4.0 — Extended.** The remaining algorithms (leaky bucket, fixed window, sliding-window log, sliding-window counter), each behind the `Limiter` trait with its own over-admit proof, plus the Tier-2 builder.
