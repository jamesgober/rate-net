# rate-net v2.0.0 — Unresettable

**Flooding the limiter no longer resets anyone's limit.** `2.0.0` closes the last eviction loophole from the October audit: a key evicted at capacity while still limited now comes back no more permissive than it left, instead of with a fresh allowance — and by default that holds however large the flood (`Overflow::FailClosed`). It is a major release because that default is a behaviour you can observe, and because it carries two long-deferred cleanups: `error-forge` becomes an optional feature and `DynLimiter` requires `Send + Sync`. It also stores per-key state a third smaller, checks long keys without allocating, finishes the HTTP surface — per-key quotas, key-length limits, bounded async waits, the current IETF structured headers, `tower` middleware — and adds guardrails that tell operators when the store is running out of room before anyone is affected. This release was prepared as `1.2.0`, which was never published.

## Highlights

- A key evicted while still limited resumes with its debt instead of a fresh allowance, so a flood of throwaway keys cannot reset a target's limit (login attempts for one username, requests for one API key) — by default, however large the flood.
- Debts are kept exactly — no other key is affected — while a store's still-limited evicted keys fit about twice its cap. Past that, the default `Overflow::FailClosed` never resets a key but may deny some keys that owed nothing; `Overflow::Forget` is the availability-first opt-out.
- Guardrails: `recovery_load()` (a gauge to alert on before anything spills or is refused), `Metrics::keys_refused` (the saturation counter), rate-limited `tracing` warnings, and a capacity sizing guide.
- `check_bytes` checks a key of any length without allocating (a 36-byte UUID: 52 ns, against 81 ns through `check`).
- `tower` middleware: `RateLimitLayer` puts a limiter in front of any axum, hyper, or tonic service, with peer-IP, verified `X-Forwarded-For`, header, and closure key extractors.

## Breaking changes

### Evicted, still-limited keys keep their debt; the default overflow policy is `FailClosed`

In 1.x every key evicted at capacity came back with a fresh allowance. In 2.0 its debt is recorded and restored when it returns. While the store's still-limited evicted keys fit about twice the cap (the binding quantity is the rate at which still-limited keys are evicted times their recovery time), nothing else changes: no key that owed nothing is affected. Past that bound the default, `Overflow::FailClosed`, keeps every debt in a shared sketch, so:

- some keys that never owed anything may start partly or wholly drained, and
- a shard saturated with still-limited keys refuses a newcomer with a retry time (`Metrics::keys_refused`).

Measured (ManualClock, 128 shards): newcomers after a drain flood are never denied up to 3x the cap (cap 100,000), about 3 % at 4x, 38 % at 6x, 86 % at 9x; a well-behaved population of 10x the cap (cap 10,000) sees 4 % false denials at 5,000 visits a second and 72 % at 20,000.

**Why:** a limit that a flood can reset is not a limit for anything keyed by identity — usernames, API keys, accounts. Secure by default; availability is an explicit choice.

**Migration:** size the cap so the bound is never reached — `cap >= peak distinct keys active within the longest recovery window × 1.5–2` — and alert on `recovery_load()` (about 0.7 utilization) and any `keys_refused`; enable the `tracing` feature for warnings. For availability-first limiters (anonymous per-IP load shedding), restore 1.x behaviour past the bound:

```rust
use rate_net::{Eviction, Overflow, RateLimiter};

let limiter = RateLimiter::builder()
    .per_second(50)
    .eviction(Eviction::default().with_overflow(Overflow::Forget))
    .build();
```

### `error-forge` is an optional feature

The `error_forge::ForgeError` impls on `RateLimiterError` and `InsufficientCapacity` now need the `forge` feature, off by default. Nothing in the limiter needs it, and the default build drops 8 crates (16 → 8 normal dependencies, `parking_lot` and a proc-macro among them).

**Migration:** `rate-net = { version = "2", features = ["forge"] }` if you use `ForgeError`.

### `DynLimiter` requires `Send + Sync`

`Arc<dyn DynLimiter>` is now shareable across threads as written. A limiter type that is not `Send + Sync` no longer implements `DynLimiter`.

**Migration:** none for `RateLimiter` users; `dyn DynLimiter + Send + Sync` still works and can be shortened to `dyn DynLimiter`.

## Added

- `Eviction::with_overflow(Overflow::FailClosed | Overflow::Forget)` and `Eviction::overflow()`; `Overflow` is `#[non_exhaustive]`, `FailClosed` the default.
- Saturation guardrails: `RateLimiter::recovery_load()` → `RecoveryLoad` (debts held against the exact capacity, overall and in the fullest shard; feature `metrics`); the `tracing` feature, which logs a `warn!` (target `rate_net::eviction`) on the first spill, drop, or saturation refusal and at most once a minute while they continue, with nothing on the check path.
- `RateLimiter::check_bytes`, `check_n_bytes`, `peek_bytes` — look a key up by a borrowed view; an existing key's check allocates nothing whatever its length.
- `Builder::quota_for(|key| …)` — per-key quota overrides from one limiter: free and paid tiers, internal callers, or a blocked tenant. The resolver runs on the caller's thread before any lock is taken, so it never blocks other keys and may call into the limiter for other keys. An override that `try_build` would reject makes its key fail closed. `RateLimiter::quota_of(key)` reports the quota a key is under.
- `Builder::max_key_len` (refuse over-long keys) and `Builder::digest_keys_longer_than` (store long keys as a 16-byte keyed digest), so a store's memory is bounded in bytes, not just keys.
- `rate_net::tower` (feature `tower`): `RateLimitLayer`, with `PeerIp`, `ForwardedFor::trusting(n)` (plus `.only_from(network, prefix_len)` to use the header only from your proxies' network), `HeaderKey` (values over 64 bytes stored as a digest), and closure extractors. Denied requests get `429` with `Retry-After` and the rate-limit headers and never reach your service. `with_anonymous(Anonymous::Shared | Key(key) | Reject(status))` decides what happens to requests with no identity; `with_cost(n)` charges `n` units (a cost of `0` counts as `1`); `RateLimit-Policy` describes the quota the key is actually under.
- `Snapshot::ratelimit("policy")` and `Quota::ratelimit_policy("policy")` — the current IETF draft's structured `RateLimit` and `RateLimit-Policy` field values, formatted without allocating.
- `until_ready_within` / `until_ready_n_within` on `AsyncLimiter` and `DirectLimiter`, and `with_jitter(max)`.
- `Metrics`: `keys_remembered`, `keys_restored`, `debts_forgotten`, `debts_overflowed`, `keys_refused`, `keys_rejected`.
- `Key::len`, `Key::is_empty`, and `From<[u8; N]>` / `From<&[u8; N]>` for `Key`.
- The `forge` and `tracing` features.
- Fuzz targets, liveness tests, a migration guide (`docs/MIGRATION_1_TO_2.md`), and a capacity sizing guide.

## Changed

- **Typed per-key state.** A key holds exactly its algorithm's state, with no enum tag, and the token bucket keeps `better-bucket`'s clock-free `BucketCore`; the limiter reads the clock once, just before the key's accounting. Heap per key at the default cap fell from ~202 B to ~138 B (~140 MiB at the 1,048,576-key default). A quota that admits nothing is never stored.
- The recovery tables are allocated per shard on first need and cost 64 bytes per key of capacity with `FailClosed`, 32 with `Forget` (about 202 or 170 MiB in all at the default cap under eviction pressure).
- `better-bucket` is used without features (only `BucketCore`), so it no longer pulls `clock-lib` and `error-forge` in a second time.
- The repository commits `Cargo.lock`, pins its development toolchain in `rust-toolchain.toml` (not packaged), and CI selects every toolchain explicitly; none of this affects users of the crate.

## Fixed

- **Long keys allocated on every check (RN-011).** `check_bytes` and friends.
- **A key whose quota admits nothing** took the shard write lock on every check, so hammering it slowed every key in its shard (same-shard p99.9 30.9 µs with 8 threads). It is now denied before any lock (1.5 µs).
- **`ForwardedFor::only_from`** compares IPv4-compatible peers and IPv4-mapped networks as IPv4 (`::ffff:10.0.0.0/104` is `10.0.0.0/8`), and a `/0` network matches every peer.
- **Clock-sensitive doc examples** run on a frozen `ManualClock`; tautological hardening assertions replaced with real ones; the contended benchmark is per-check latency (earlier figures withdrawn).

## Security

- **Limit reset by flooding (RN-005).** An attacker who wanted to reset a target's limit only had to send enough throwaway keys to push the target out of the store. Eviction now prefers keys whose allowance has fully recovered, and records the debt of any key it evicts before then; by default no flood resets a key. Two fail-opens found while reviewing this release are fixed before it: a key with a slow per-key quota that expired by idle TTL after spending again was forgotten with its debt, and the overflow sketch under-charged window keys with a limit above 16,777,215. Regression tests fail against `1.1.0` for all five algorithms; `loom` models cover eviction racing a check, concurrent record-and-take, and the idle sweep racing a re-check; property tests check that no recorded debt is ever lost; a fuzz target drives a heavily evicting store with slow per-key tiers and idle TTLs against a token-bucket oracle.
- **Unbounded key bytes (RN-006).** `max_key_len` and `digest_keys_longer_than` bound them; `HeaderKey` digests header values longer than 64 bytes by default.
- **Forged `X-Forwarded-For`.** `.only_from(network, prefix_len)` uses the header only when the connection's peer is inside your proxies' network and keys by the peer otherwise, so a client that reaches the service directly cannot choose its key.

## Performance

Criterion medians, per check (Windows 11 x86_64, 32 logical CPUs, Rust 1.99, fat LTO). The host was shared with other builds throughout; `v1.1.0` and `v2.0.0` were run alternately on it, best run of each shown, so treat ~10 % as noise.

| Path | v1.1.0 | v2.0.0 |
|------|-------:|-------:|
| Single-key check | 60.6 ns | 59.1 ns |
| Single-key check on `CoarseClock` | 36.3 ns | 37.5 ns |
| Many-key check (64 shards) | 64.0 ns | 55.4 ns |
| One key, 4 threads contending (per check) | 223 ns | 229 ns |
| 36-byte key: `check` / `check_bytes` | 87.2 ns / — | 80.9 ns / 52.4 ns |
| New key at the default cap (insert + evict) | 293 ns | 351 ns |
| `peek` | 80.4 ns | 54.1 ns |
| A key whose quota admits nothing | — | 53 ns |

The new-key-at-cap row is a known issue (below): +58 ns, because eviction reads each candidate's state so that it never resets a still-limited key. In a second, less noisy measurement (one fresh process per run, pinned to a core, variants alternated over six rounds) the medians were ~242 ns for `1.1.0` and ~250 ns for `2.0.0`.

Under a unique-key flood at the default cap, a legitimate key's check stays at p99.9 ≈ 0.5–1.3 µs (1.2 µs when every evicted flood key owes a debt, under the default `FailClosed`), against 0.3 µs with no flood; the audit measured 128 µs for `1.0.0`. The guardrails add nothing to the check path (`check/single_key` within noise with `tracing` on). Full method, per-policy rows, and the liveness measurements are in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md).

## Known issues

- **Inserting a new key into a full store costs ~58 ns more than in 1.1.0.** When the key table is at its cap, inserting a never-seen key costs about +58 ns (≈293 → 351 ns at the default 1,048,576-key cap; measured on a loaded Windows host, best of runs, so approximate) because eviction checks that each candidate has fully recovered before evicting it — the price of never resetting a still-limited key. Checks of keys already tracked are unaffected, and below the cap nothing changes. It is to be optimised in a future release and is a blocker for the next minor release, 2.1.0.
- **Past about twice the cap of still-limited evictions, `FailClosed` denies some keys that owed nothing.** Newcomers after a drain flood: 0 % up to 3x the cap, about 3 % at 4x, 38 % at 6x, 86 % at 9x; a well-behaved population of 10x the cap: 4 % false denials at 5,000 visits a second, 72 % at 20,000. Size the cap so it never gets there, alert on `recovery_load()` and `keys_refused`, or opt into `Overflow::Forget` — which denies none of them but lets a sustained flood reset evicted keys over and over (in a real-clock race at cap 32, drained victims were admitted hundreds of thousands of units over their bound).
- **Under `FailClosed`, a shared overflow charge** cannot be cleared for one key by `reset` or `remove` (it expires within one recovery period; `clear` drops it at once), and a slow tier's charge can drain a fast-tier newcomer for the slow tier's recovery time.
- **`clock-lib` 1.1.0 does not build under `--cfg loom`**, so the `loom` job runs against `clock-lib` 1.0.0; the fix belongs upstream.

## Migration guide

See [`docs/MIGRATION_1_TO_2.md`](https://github.com/jamesgober/rate-net/blob/main/docs/MIGRATION_1_TO_2.md). In short:

1. `rate-net = "2"`.
2. If you use `error_forge::ForgeError` on rate-net's errors, add `features = ["forge"]`.
3. Size the cap (`cap >= peak distinct keys active within the longest recovery window × 1.5–2`), export `recovery_load()` and `keys_refused`, and enable `tracing` for warnings.
4. For availability-first limiters only, opt back into 1.x behaviour past the bound with `Eviction::with_overflow(Overflow::Forget)`.
5. If you implemented `DynLimiter` (through `Limiter`) for a type that is not `Send + Sync`, it no longer qualifies.
