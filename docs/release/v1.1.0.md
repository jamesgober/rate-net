# rate-net v1.1.0 — Hardened

**The limiter now holds its guarantees under real contention.** `1.1.0` fixes a real-clock over-admission in the default token bucket, an O(n) eviction scan that a unique-key flood could turn into a CPU and latency denial of service, and a set of window-algorithm bugs — and adds the surface HTTP services kept asking for: validated configuration, `peek` snapshots with `Retry-After` / `RateLimit-*` helpers, key management, safe keys, a direct limiter, a `no_std` core, and a fast clock. Every change is additive or a bug fix; `rate-net = "1"` picks it up with no source changes.

## What is rate-net?

A rate limiter for Rust. It answers one question — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. Five algorithms behind one `Limiter` trait, per-key state in a sharded store bounded by O(1) eviction, hardened against adversarial traffic, with a frozen public API validated against a representative gatekeeper consumer.

## What's fixed

### Over-admission under contention (critical)

With two or more threads on one key and a real clock, the default token bucket admitted 20x to 600x its quota: a thread holding a timestamp a moment older than the bucket's last update read the negative gap as a ~49.7-day refill. The bug lived in `better-bucket` 1.0 and is fixed in `better-bucket` 1.1, which rate-net now requires. Every concurrency test in `1.0` froze the clock, which is why nothing caught it; `1.1` adds real-clock contention tests for every algorithm (2, 4, and 8 threads on one key on the OS clock) and `loom` models of the production limiter in which a thread reads the clock, stalls, and lands after another thread's later commit.

The fixed window had the same class of bug — a late thread rolled the window back and let the newer window admit a second full quota — plus a `u32` overflow once `limit > u32::MAX / 2`. Both are fixed, and the sliding-window algorithms now treat late threads conservatively too.

### Eviction is O(1)

At capacity, `1.0` scanned the whole shard for its least-recently-seen key on every new key — ~329 µs per insert at the default cap, under the shard write lock, with one existing-key check measured waiting 608 ms during a flood. An idle TTL ran a full-shard `retain` on every insert. `1.1` evicts by CLOCK with a scan bounded at 32 slots and drains the idle TTL incrementally (8 slots per insert): an insert at the default cap now costs ~0.36 µs. The only shard-wide pass left is the amortized growth or rehash of a shard's index; capped shards are kept to 16,384 keys (the shard count is raised as needed), so that pass takes a few milliseconds at worst instead of ~200 ms for a 1M-key shard.

### Fail closed

A zero period used to admit *everything* under four of the five algorithms; the leaky bucket over-admitted 1.67x at 600 M/s from a truncated interval and admitted everything above 1 G/s. Every degenerate configuration now denies everything, the leaky bucket accounts in exact emission intervals, and `Builder::try_build` names the problem instead. An idle TTL can no longer reset a key's quota early: it is raised to the quota's recovery time.

## What's new

- **`Builder::try_build`** — validated construction (`ZeroQuota`, `ZeroPeriod`, `ZeroBurst`, `RateTooHigh`, `LimitTooLarge`, `IdleTtlTooShort`). `build` stays infallible and fails closed.
- **`peek` → `Snapshot`** — a key's capacity, remaining units, and time until whole, without spending anything or creating state.
- **HTTP helpers** — `Decision::retry_after_secs` (rounded **up**: no early retries), `Decision::is_impossible`, `Snapshot::headers` for `RateLimit-Limit` / `-Remaining` / `-Reset`, and the `headers` module of names.
- **Key management** — `reset`, `remove`, `clear`, `retain_recent` (lossless), `shrink_to_fit`.
- **Safe keys** — tagged `Key::id` and `Key::ip` that can never collide with attacker-chosen strings, and `Key::ipv6_prefix` / `Key::ip_prefix` so an IPv6 client cannot rotate through its `/64`. `Key`'s `Debug` no longer prints key bytes.
- **`DirectLimiter`** — one stream, no key, no map, no shard lock.
- **`Gcra`** — the `no_std`, clock-free single-key core, delivering the `no_std` mode `1.0` promised.
- **`CoarseClock`** — a monotonic clock read with one atomic load; with it a keyed check takes ~35 ns instead of ~66 ns and a direct check ~8 ns.
- **`try_until_ready`** on `AsyncLimiter` and `DirectLimiter` — returns `InsufficientCapacity` instead of returning as if admitted.
- **`metrics` feature** — allowed / denied / inserted / evicted / expired / removed counters, compiled out when off.
- **`DynLimiter`** — an object-safe face of `Limiter` for `Box<dyn …>` / `Arc<dyn …>` middleware.

## Benchmarks at `v1.1.0`

Criterion medians (Windows x86_64, Rust 1.95, `opt-level = 3`):

| Path | v1.0.0 | v1.1.0 |
|------|-------:|-------:|
| Single-key check | 66.3 ns | 66.2 ns |
| Single-key check on `CoarseClock` | — | 35.0 ns |
| Many-key check (64 shards) | 86.6 ns | 54.9 ns |
| Contended single key (4 threads, aggregate) | 151.9 ns/op | 49.5 ns/op |
| New key at the default cap (insert + evict) | ~329 µs | 0.36 µs |
| `DirectLimiter` check on `CoarseClock` | — | 8.2 ns |

The `1.0.0` column is a re-measurement of the `1.0.0` code; the figures `1.0.0` published could not be reproduced and are withdrawn. Against `governor` 0.10 on the default clock, `governor` is still faster on a keyed check (~20 ns vs ~52 ns), mostly because of its TSC clock; on `CoarseClock` the direct paths are at parity (8.6 vs 8.3 ns). Full method and analysis in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md).

## Corrected documentation

`1.0` overstated several things, and this release says what is true: the check path is not lock-free (a shard read lock plus atomic accounting; the sliding windows take a per-key mutex); the `loom` suite now checks the real code rather than a hand-written copy; eviction no longer blocks the check path because it is now bounded; per-key memory is documented (~200–300 bytes, ~202 MiB at the default cap, down from ~514 MiB); the CI platform list is stated as tested; and the README Quick Start compiles — the README and API reference now run as doctests.

## Breaking changes

None. No public item was removed or changed. `AsyncLimiter::until_ready` / `until_ready_n` are **deprecated** (they return as if admitted when a request can never fit) in favour of `try_until_ready` / `try_until_ready_n`; they remain until `2.0`.

Behaviour changes are bug fixes: degenerate configurations now deny rather than admit; an idle TTL shorter than the quota's recovery time is raised to it; `Key`'s `Debug` output is redacted.

## Upgrade

```toml
[dependencies]
rate-net = "1.1"

# Full algorithm suite, async waiting, and metrics:
rate-net = { version = "1.1", features = ["algorithms", "async", "metrics"] }
```

`rate-net` 1.1 requires `better-bucket` 1.1, which Cargo resolves automatically. If you call `until_ready`, switch to `try_until_ready` and handle `InsufficientCapacity`. If you build from configuration, prefer `try_build`. MSRV: Rust 1.85.
