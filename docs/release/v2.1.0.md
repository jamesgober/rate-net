# rate-net v2.1.0: Shared parameters

**The leaky-bucket arithmetic now runs over state you store yourself, and inserting a new key into a full store costs what it did in 1.1.0 again.** `2.1.0` is additive: nothing existing changes behaviour, and `rate-net = "2"` picks it up with no source changes.

## Highlights

- `GcraParams` holds a quota's GCRA parameters once and checks any number of 8-byte words against them, so a keyed table of your own can keep each key's limiter state beside the key, in one cache line.
- `Gcra` is rebuilt on `GcraParams`: one copy of the arithmetic, the same decisions, the same 80 bytes, the same speed.
- The at-capacity insert regression that `2.0.0` shipped as a known issue is gone: ~219 ns per insert at the default 1,048,576-key cap, against ~220 ns for `1.1.0` and ~233 ns for `2.0.1`, and 88 ns on a 64-key shard, against 97 ns and 146 ns.

## Added

### `GcraParams`

A `Gcra` carries its quota's parameters, about 80 bytes, in every instance. A keyed limiter that tracks many streams under one quota needs them only once. `GcraParams` is that half of a `Gcra`: build it from a `Quota`, and pass it the stream's theoretical arrival time, a `core::sync::atomic::AtomicU64` that you store wherever suits your table.

```rust
use core::sync::atomic::AtomicU64;
use core::time::Duration;
use rate_net::{GcraParams, Quota};

// One set of parameters for a whole tier; one word per key.
let params = GcraParams::new(Quota::per_second(10).with_burst(2));
let tat = AtomicU64::new(0); // a full bucket, stored with the key

assert!(params.check_n_at(&tat, 2, Duration::ZERO).is_allow());
assert_eq!(
    params.check_at(&tat, Duration::ZERO).retry_after(),
    Some(Duration::from_millis(100)),
);
assert_eq!(params.peek_at(&tat, Duration::from_millis(100)).remaining(), 1);
params.reset(&tat); // the same as storing 0
```

- `new(quota)` fails closed (a zero limit, period, or burst admits nothing; a rate finer than one unit per nanosecond is clamped to it); `try_new(quota)` rejects those with `ZeroQuota`, `ZeroPeriod`, `ZeroBurst`, or `RateTooHigh`.
- `check_at(&tat, now)`, `check_n_at(&tat, n, now)`, `peek_at(&tat, now)`, `reset(&tat)`, and `quota()`.
- A word of `0` is a full bucket. Any other value counts emission intervals of the quota it was written under, so use a word with one set of parameters only. Checks update the word with a compare-and-swap, so any number of threads may check it at once, and a denial leaves it unchanged.
- `Clone`, `Copy`, `PartialEq`, `Eq`, `Debug`, `Send + Sync`; part of the `no_std` core on every target with 64-bit atomics.
- `Gcra::params()` returns the parameters a `Gcra` runs on, and `examples/shared_params.rs` shows a small keyed table built on them.

## Changed

- `Gcra` is now one theoretical arrival time plus a `GcraParams`. Its decisions, `retry_after` values, snapshots, and size are unchanged: `tests/gcra_params.rs` checks `GcraParams`, `Gcra`, and a frozen copy of the `2.0.1` implementation against each other across random quotas (zero limits and bursts, rates past one per nanosecond, non-integral intervals), `n` from `0` to past the burst, and times that step back or saturate, comparing every decision, snapshot, and stored word. `gcra/check_at` measures 6.87 to 6.89 ns against 6.88 to 6.91 ns for `2.0.1` in alternating runs.

## Performance

### The at-capacity insert is back to 1.1.0's cost

`2.0.0` reported inserting a never-seen key into a full store at ~58 ns slower than `1.1.0`. Measured with each version as its own binary, pinned to one core, alternated round by round, the gap was +16 ns (+7 %); the larger figure was mostly scheduler noise on a loaded host. Switching pieces off one at a time put all of it on one line: the exact "recovers at" hint computed for every key as it was stored, which for the token bucket costs two 128-bit divisions in `better-bucket` and a third in rate-net's millisecond rounding. Reading eviction candidates was never the cost.

`2.1.0` keeps the hint but skips the arithmetic where it is not needed. A fresh key that spent nothing is whole; one that is whole again within the millisecond gets its exact (rounded-up) hint from one fullness check; only a key that still owes past that pays for the exact time. The eviction sweep also confirms a hint due within the current millisecond with one cheap read, which is what made small shards slower. A hint is still never earlier than the truth, so a still-limited key is never mistaken for a recovered one and evicted without its debt.

| Per insert, pinned medians | `1.1.0` | `2.0.1` | `2.1.0` |
|-----------------------------|--------:|--------:|--------:|
| New key at the default cap | 220 ns | 233 ns | 219 ns |
| New key, 64-key shard | 97 ns | 146 ns | 88 ns |

Checks of tracked keys are unchanged. Where every evicted key still owes (a drain flood), `2.1.0` and `2.0.1` do the same work, recording each debt; that is the cost of `2.0`'s no-reset guarantee, which `1.1.0` did not give. Method and full results: [`docs/BENCHMARKS.md`](../BENCHMARKS.md#new-key-at-capacity-resolved-in-210).

## Known issues

Unchanged from `2.0.0`: past about twice the cap of still-limited evictions, `Overflow::FailClosed` (the default) denies some keys that owed nothing. Size the cap, alert on `recovery_load()` and `keys_refused`, or opt into `Overflow::Forget`. See the README's "Sizing the cap".
