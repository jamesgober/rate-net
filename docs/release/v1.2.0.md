# rate-net v1.2.0 — Unresettable

**Flooding the limiter can no longer reset anyone's limit.** `1.2.0` closes the last eviction loophole from the October audit: a key evicted at capacity while still limited now comes back no more permissive than it left, instead of with a fresh allowance. It also stores per-key state a third smaller, checks long keys without allocating, and finishes the HTTP surface — per-key quotas, key-length limits, bounded async waits, the current IETF structured headers, and `tower` middleware. It is a minor release (`cargo semver-checks`: no public item removed or changed); read **Changed** and **Known issues** for the behaviours you can observe.

## Highlights

- A key evicted while still limited resumes with its debt instead of a fresh allowance, so a flood of throwaway keys cannot reset a target's limit (login attempts for one username, requests for one API key).
- Debts are kept exactly — no other key is affected — while a store's still-limited evicted keys fit in about twice its cap; beyond that the store fails closed for some keys, never open.
- `check_bytes` checks a key of any length without allocating (a 36-byte UUID: 52 ns, against 81 ns through `check`).
- `tower` middleware: `RateLimitLayer` puts a limiter in front of any axum, hyper, or tonic service, with peer-IP, verified `X-Forwarded-For`, header, and closure key extractors.
- Per-key quotas (`Builder::quota_for`), key-length limits, bounded async waits with jitter, and the IETF `RateLimit` / `RateLimit-Policy` structured fields.

## Added

- `RateLimiter::check_bytes`, `check_n_bytes`, `peek_bytes` — look a key up by a borrowed view; an existing key's check allocates nothing whatever its length.
- `Builder::quota_for(|key| …)` — per-key quota overrides from one limiter: free and paid tiers, internal callers, or a blocked tenant. The resolver runs on the caller's thread before any lock is taken, so it never blocks other keys and may call into the limiter for other keys. An override that `try_build` would reject makes its key fail closed. `RateLimiter::quota_of(key)` reports the quota a key is under.
- `Builder::max_key_len` (refuse over-long keys) and `Builder::digest_keys_longer_than` (store long keys as a 16-byte keyed digest), so a store's memory is bounded in bytes, not just keys.
- `rate_net::tower` (feature `tower`): `RateLimitLayer`, with `PeerIp`, `ForwardedFor::trusting(n)` (plus `.only_from(network, prefix_len)` to use the header only from your proxies' network), `HeaderKey` (values over 64 bytes stored as a digest), and closure extractors. Denied requests get `429` with `Retry-After` and the rate-limit headers and never reach your service. `with_anonymous(Anonymous::Shared | Key(key) | Reject(status))` decides what happens to requests with no identity; `with_cost(n)` charges `n` units (a cost of `0` counts as `1`); `RateLimit-Policy` describes the quota the key is actually under. Adds `http`, `tower-layer`, `tower-service`, and `pin-project-lite` — not `tower` itself.
- `Snapshot::ratelimit("policy")` and `Quota::ratelimit_policy("policy")` — the current IETF draft's structured `RateLimit` and `RateLimit-Policy` field values, formatted without allocating.
- `until_ready_within` / `until_ready_n_within` on `AsyncLimiter` and `DirectLimiter` — wait only while the next admission fits the budget, otherwise return the denial at once; `with_jitter(max)` spreads out tasks denied together.
- `Metrics`: `keys_remembered`, `keys_restored`, `debts_overflowed`, `keys_refused`, `keys_rejected`.
- `Key::len`, `Key::is_empty`, and `From<[u8; N]>` / `From<&[u8; N]>` for `Key`.
- Fuzz targets for the limiter (against a token-bucket oracle) and the HTTP surface; liveness tests (`tests/eviction_liveness.rs`) beside the safety tests.

## Changed

- **An evicted, still-limited key keeps its debt.** In `1.1.0` such a key came back with a fresh allowance. Now its shard records what it owed, and it resumes exactly where it was (token and leaky buckets) or with the spent units charged at its return (window algorithms, which may be held back up to one window longer). The debts live in a cuckoo-hashed table of 16-byte records, two per key of capacity: a key reads back only its own record, so while a store's still-limited evicted keys fit — about twice its cap at once — no other key is ever charged and nothing is refused.
- **Past that bound the store fails closed for some keys.** Debts that do not fit spill into a shared sketch that charges a key the smaller of two cells. That never undercharges the key that spilled, but a key that never owed anything can start partly or wholly drained, and a full shard holding only still-limited keys refuses a newcomer with a retry time. A key charged this way never writes the charge back, so it cannot spread or ratchet. Measured rates are under **Known issues**.
- **Typed per-key state.** A key holds exactly its algorithm's state, with no enum tag, and the token bucket keeps `better-bucket`'s clock-free `BucketCore`; the limiter reads the clock once, just before the key's accounting. Heap per key at the default cap fell from ~202 B to ~138 B (~140 MiB at the 1,048,576-key default). A quota that admits nothing is never stored.
- The recovery table is allocated per shard on first need and costs 64 bytes per key of capacity (64 MiB at the default cap).
- `better-bucket` is used without features (only `BucketCore`), so it no longer pulls `clock-lib` and `error-forge` in a second time.
- The repository now commits `Cargo.lock`, pins its development toolchain in `rust-toolchain.toml` (not packaged), and CI selects every toolchain explicitly; none of this affects users of the crate.

## Fixed

- **Capacity eviction reset still-limited keys (audit RN-005).** See **Security**.
- **Long keys allocated on every check (RN-011).** `check_bytes` and friends.
- **Tautological hardening assertions** in `tests/hardening.rs` replaced with real ones; every integration test follows the REPS naming convention.
- **Clock-sensitive doc examples** that asserted reset times now run on a frozen `ManualClock`, so a stalled host cannot fail them.
- **The contended benchmark** reported aggregate throughput across four threads, about four times faster than any caller sees; it is now per-check latency. The earlier figures are withdrawn.

## Security

- **Limit reset by flooding (RN-005).** An attacker who wanted to reset a target's limit only had to send enough throwaway keys to push the target out of the store. Eviction now prefers keys whose allowance has fully recovered, and records the debt of any key it evicts before then. Regression tests fail against `1.1.0` for all five algorithms; a `loom` model covers a drained key being evicted while it is checked; a property test checks that no recorded debt is ever lost; a fuzz target drives a heavily evicting store against a token-bucket oracle.
- **Unbounded key bytes (RN-006).** `max_key_len` and `digest_keys_longer_than` bound them; `HeaderKey` digests header values longer than 64 bytes by default.
- **Forged `X-Forwarded-For`.** `ForwardedFor` keys by the address your trusted proxies appended only if every request reaches the service through them. `.only_from(network, prefix_len)` uses the header only when the connection's peer is inside your proxies' network and keys by the peer otherwise, so a client that reaches the service directly cannot choose its key.

## Performance

Criterion medians, per check (Windows 11 x86_64, 32 logical CPUs, Rust 1.99, fat LTO). The host was shared with other builds throughout; `v1.1.0` and `v1.2.0` were run alternately on it, best run of each shown, so treat ~10 % as noise.

| Path | v1.1.0 | v1.2.0 |
|------|-------:|-------:|
| Single-key check | 60.6 ns | 59.1 ns |
| Single-key check on `CoarseClock` | 36.3 ns | 37.5 ns |
| Many-key check (64 shards) | 64.0 ns | 55.4 ns |
| One key, 4 threads contending (per check) | 223 ns | 229 ns |
| 36-byte key: `check` / `check_bytes` | 87.2 ns / — | 80.9 ns / 52.4 ns |
| New key at the default cap (insert + evict) | 293 ns | 351 ns |
| `peek` | 80.4 ns | 54.1 ns |

The new-key-at-cap row is a known issue (below): +58 ns, because eviction reads each candidate's state so that it never resets a still-limited key. In a second, less noisy measurement (one fresh process per run, pinned to a core, variants alternated over six rounds) the medians were ~242 ns for `1.1.0` and ~250 ns for `1.2.0`.

Under a unique-key flood at the default cap, a legitimate key's check stays at p99.9 0.6–1.3 µs (1.3 µs when every evicted flood key still owes a debt), against 0.3–0.7 µs with no flood; the audit measured 128 µs for `1.0.0`. Full method and the liveness measurements are in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md).

## Documentation

- `docs/API.md`, the README, and the rustdoc describe the eviction guarantee as built: exact within about twice the cap, fail-closed past it, with measured rates.
- The README has **Known issues** and **Development** (toolchain and lockfile policy) sections; its testing commands create the fuzz corpus directories and pin `clock-lib` for the `loom` run.

## Known issues

- **Inserting a new key into a full store costs ~58 ns more than in 1.1.0.** When the key table is at its cap, inserting a never-seen key costs about +58 ns (≈293 → 351 ns at the default 1,048,576-key cap; measured on a loaded Windows host, best of runs, so approximate) because eviction checks that each candidate has fully recovered before evicting it — the price of never resetting a still-limited key. Checks of keys already tracked are unaffected, and below the cap nothing changes. It is planned to be revisited and optimised in a future release.
- **Past about twice the cap of still-limited evictions, some keys that owed nothing are charged.** Measured with a `ManualClock` and 128 shards: after a flood of unique keys that each drain their quota, 0 % of newcomers are denied up to a flood of 3x the cap (cap 100,000), about 3 % at 4x and 39 % at 6x; a well-behaved population of 3x the cap (cap 10,000) sees no false denials, 10x the cap about 4 %. `1.1.0` denied none of them, because it forgot every debt. `debts_overflowed` and `keys_refused` (feature `metrics`) show when a cap is too small for the traffic.
- **`reset` and `remove` cannot clear a shared overflow charge for one key**; it expires within one recovery period, and `clear` drops it at once.
- **`clock-lib` 1.1.0 does not build under `--cfg loom`**, so the `loom` job runs against `clock-lib` 1.0.0; the fix belongs upstream.
- `error-forge` stays tied to the `std` feature (making it optional would be breaking; recorded for `2.0`), and the default capacity stays at 1,048,576 keys.

## What's next

- Resolve the new-key-at-capacity cost (above) without weakening the no-reset guarantee — a blocker for `1.3.0`.
- A lock-free read path for existing keys, once it can be model-checked as thoroughly as the current store.
