# rate-net v1.2.0 — Unresettable

**Flooding the limiter can no longer reset anyone's limit.** `1.2.0` closes the last eviction loophole from the October audit: a key evicted at capacity while still limited now comes back exactly as limited as it left. It also stores per-key state a third smaller, checks long keys without allocating, and finishes the HTTP surface — per-key quotas, key-length limits, bounded async waits, the current IETF structured headers, and `tower` middleware. Every change is additive or a fix; `rate-net = "1"` picks it up with no source changes.

## What is rate-net?

A rate limiter for Rust. It answers one question — *"is this key allowed right now?"* — and returns a decision plus a `retry-after`, tracking an independent allowance per key. Five algorithms behind one `Limiter` trait, per-key state in a sharded store bounded by O(1) eviction, hardened against adversarial traffic.

## What's fixed

### Eviction never resets a limit

A limiter that tracks per-key state has to forget keys when a flood of unique keys fills its store. Until now, forgetting a key that was still being limited handed it a fresh allowance when it came back: an attacker who wanted to reset a target's limit — login attempts for one username, requests for one API key — only had to send enough throwaway keys to push the target out of the store.

`1.2.0` removes that lever. The eviction sweep prefers keys whose allowance has fully recovered, since forgetting those loses nothing. When it must evict a key that has not recovered, the shard records what the key owes — the units it spent and when they would all be back — in a small table (16 bytes a record, allocated on first use). A key that returns before its debt is repaid resumes **no more permissive than it left**: exactly, to within one unit, for the token and leaky buckets; with the spent units charged at its return for the window algorithms.

The table is bounded too. If a flood evicts more still-limited keys within one recovery period than the table can hold, records merge, keeping the larger debt and the later deadline, and a merged record applies to every new key that maps to it until it expires. Under that extreme pressure the limiter **fails closed** for some newcomers instead of open for the keys it evicted. `Metrics::records_merged` tells you when it happens.

The fix is pinned by regression tests that fail against `1.1.0` for all five algorithms, a `loom` model of a drained key being evicted while it is checked, a property test, and a new fuzz target that drives a heavily evicting store with arbitrary operations against a token-bucket oracle.

### Long keys no longer allocate

`check(key)` builds an owned `Key`, and a key longer than 22 bytes — a UUID, an API token, a JWT subject — went to the heap on every call. The new `check_bytes`, `check_n_bytes`, and `peek_bytes` look keys up by a borrowed view: an existing key's check allocates nothing whatever its length, and runs ~35 % faster for a UUID.

### Memory, measured and bounded in bytes

Per-key state is now stored as the algorithm's own type rather than an enum whose tag pushed a token-bucket key onto a third cache line, and the token bucket keeps `better-bucket`'s clock-free core. Heap per key at the default cap fell from ~202 to ~138 bytes (~140 MiB at the 1,048,576-key default). `Builder::max_key_len` refuses over-long keys and `Builder::digest_keys_longer_than` stores long ones as a 16-byte keyed digest, so the bound holds in bytes, not just keys.

## What's new

- **Per-key quotas** — `Builder::quota_for(|key| …)` gives chosen keys their own quota from one limiter: free and paid tiers, internal callers, or a blocked tenant (an override that admits nothing).
- **`tower` middleware** (feature `tower`) — `RateLimitLayer` in front of any `tower::Service` over `http` (axum, hyper, tonic), with `PeerIp`, `ForwardedFor` (trusting a fixed number of proxies, never a client-written entry), `HeaderKey`, and closure key extractors. Denied requests get `429` with `Retry-After` and the rate-limit headers and never reach your service.
- **Structured `RateLimit` headers** — `Snapshot::ratelimit("policy")` and `Quota::ratelimit_policy("policy")` format the current IETF draft's `RateLimit` and `RateLimit-Policy` field values, without allocating.
- **Bounded waits and jitter** — `until_ready_within(key, max_wait)` on `AsyncLimiter` and `DirectLimiter` waits only while the next admission fits the budget and otherwise returns the denial at once; `with_jitter(max)` spreads out tasks denied together.
- **More metrics** — `keys_remembered`, `keys_restored`, `records_merged`, `keys_rejected`.
- **Keys** — `Key::len`, `Key::is_empty`, and `From<[u8; N]>` / `From<&[u8; N]>`.
- **Fuzzing** — `fuzz/` targets for the limiter and the HTTP surface, smoke-run in CI.

## Benchmarks at `v1.2.0`

Criterion medians, per check (Windows x86_64, 32 logical CPUs, Rust 1.99, fat LTO). The host was shared with other builds throughout; `v1.1.0` and `v1.2.0` were run alternately on it, best run of each shown.

| Path | v1.1.0 | v1.2.0 |
|------|-------:|-------:|
| Single-key check | 60.6 ns | 59.1 ns |
| Single-key check on `CoarseClock` | 36.3 ns | 37.5 ns |
| Many-key check (64 shards) | 64.0 ns | 55.4 ns |
| One key, 4 threads contending (per check) | 223 ns | 229 ns |
| 36-byte key: `check` / `check_bytes` | 87.2 ns / — | 80.9 ns / 52.4 ns |
| New key at the default cap (insert + evict) | 293 ns | 351 ns |
| `peek` | 80.4 ns | 54.1 ns |

The contended figure is now what one caller sees per check; earlier releases reported aggregate throughput across the four threads, which read about four times faster and is withdrawn. An insert at the default cap costs ~50 ns more by design — eviction now reads each candidate's state so it never resets a limit — and is still about a thousand times cheaper than `1.0.0`'s scan.

Under a unique-key flood at the default cap, a legitimate key's check stays at p99.9 ≈ 1 µs (0.7–1.4 µs, including the case where every eviction records a debt and the recovery table overflows), against 0.3–0.7 µs with no flood; the audit measured 128 µs for `1.0.0`. Full method in [`docs/BENCHMARKS.md`](https://github.com/jamesgober/rate-net/blob/main/docs/BENCHMARKS.md).

## Breaking changes

None. No public item was removed or changed (`cargo semver-checks`: no semver update required for a minor release, on default and all features). The limiter stays `Send + Sync + UnwindSafe`, now asserted in the test suite.

Behaviour changes are fixes: a key evicted while still limited resumes with its debt instead of a fresh allowance (and, under extreme eviction pressure, some new keys may start drained); a key whose quota admits nothing is no longer stored.

## Upgrade

```toml
[dependencies]
rate-net = "1.2"

# Everything: the full algorithm suite, async waiting, metrics, and tower middleware.
rate-net = { version = "1.2", features = ["algorithms", "async", "metrics", "tower"] }
```

No code changes are needed. On hot paths with long keys, switch `check(key)` to `check_bytes(key)`. If a limiter faces untrusted keys, consider `max_key_len` or `digest_keys_longer_than`. MSRV: Rust 1.85.
